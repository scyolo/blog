# 写作与发布

## 使用站内写作台

打开 [写作台](https://scyolo.github.io/blog/write/)。填写标题、文章路径、摘要、分类、标签和发布时间，编辑 Markdown 正文。桌面可使用双栏，手机可切换「写作」「预览」；公式、Mermaid、Callout、任务列表、表格和 `==高亮==` 都能预览。`[[article-slug|显示名称]]` 连接已发布文章；图片嵌入使用 `![[../../assets/images/file.png|替代文本]]`。代码块和行内代码不会被当作双链处理。

草稿自动保存到本机，最多保留 20 份。「新文章」和「导入」保留上一份草稿，可在「本机草稿」切换。旧版写作台的草稿会自动迁移。导入使用完整 YAML 解析，支持多行摘要、数组标签、带时区日期，并保留作者、封面、修改时间和示例标记。单篇文章连同元数据限 240 KB。

「导出 Markdown」生成 `draft: true` 的备份文件，不会改变线上文章。即使字段尚未填完或浏览器存储已满，仍可导出当前内容。隐私模式、清理站点数据和更换浏览器不会同步草稿，请定期导出备份；同时编辑多个标签页时，发现外部变更会停止覆盖保存。

## 首次连接 GitHub

1. 点击「连接 GitHub」，按窗口中的入口创建 **fine-grained personal access token**。
2. 所有者选 `scyolo`，仓库只选 `scyolo/blog`，权限设置为 **Contents: Read and write**、**Actions: Read-only**，并设置合理的到期时间。不需要 Workflows 写权限。
3. 在写作台的密码框中输入令牌并连接。不要把令牌发到聊天、写进 Markdown、提交到仓库或填入部署变量。

令牌只保存在当前页面的内存中，仅发送到 `https://api.github.com`。断开连接、关闭页面或刷新后需要重新连接；localStorage/sessionStorage 只保存文章，不保存授权。这里没有中转认证服务器，也不需要 Cloudflare。账户必须拥有仓库写入权限，实际权限由 GitHub API 执行。

## 直接在网站发布

1. 完成文章信息和正文，点击「发布文章」。对话框会展示标题、目标路径和是否为未来发布时间。
2. 确认后，写作台将 Markdown 提交到 `codex/github-pages` 的 `src/content/posts/`。新文章默认文件名为 `<slug>.md`。
3. GitHub Actions 自动执行内容、代码、浏览器、产物和性能检查，使用通过验证的同一份产物部署 Pages。
4. 写作台先显示「已提交」，再跟踪构建和部署。只有 `build-info.json` 的提交号与本次一致，且文章实际返回 HTTP 200，才显示「文章已上线」。可通过「查看部署进度」检查失败原因。

不需要手动下载文件、打开 Git 客户端或复制到文章目录。「已提交」不等于「已上线」：构建失败、授权过期、网络中断和部署被跳过都保留明确反馈。网络导致提交状态不确定时，先刷新仓库文章列表，避免重复提交。

发布时间统一按 **北京时间 UTC+8** 编辑；已有文章未更改时间时保留原来的秒和毫秒。未来日期可以提交，但当前没有后台定时任务，必须在日期到达后再次触发构建才会公开。

## 修改已有文章与仓库草稿

连接后在「仓库文章」选择文章并点击「载入文章」。已有文章沿用原文件路径和 slug，保留封面、作者、示例标记等元数据。再次发布时更新修改时间，不把旧文变成新文章。

如果其他设备或 GitHub 网页已经修改该文章，写作台会拒绝过期版本；如果检查后分支又出现新提交，也不会强制覆盖。先导出本机修改，再载入新版本进行合并。

「保存为仓库草稿」写入 `draft: true`。**当前仓库是公开仓库，仓库草稿原文仍可在 GitHub 查看。** 私密草稿应只保存在本机。载入已发布文章后，此按钮变为「下架这篇文章」，确认并部署完成后才从博客撤下；Git 历史不被删除。

## 新建文章

将 templates/post.md 复制到 src/content/posts/，文件名建议使用英文。先修改 slug、标题、摘要和日期，再写正文。slug 必须以小写英文字母开头，只能包含小写字母、数字和连字符，同一篇文章发布后保持不变；文件移动或标题修改不会改变文章地址。

category 只使用 knowledge（知识笔记）或 essay（随笔）。tags 用于更细的主题。时间必须带 Z 或明确时区，推荐使用带引号的 ISO 时间，例如 '2026-10-03T09:00:00+08:00'，页面显示使用北京时间。

每篇文章都必须显式写 draft。草稿使用 true，正式发布才改为 false；缺失字段不会被当作已发布。未来日期文章需要到期后再次构建才会出现，不提供自动定时发布。

## 本地检查

使用项目指定的 Node 与 pnpm，运行 pnpm dev 写作。提交前运行 pnpm validate:content、pnpm test 与 pnpm build，再使用 pnpm preview 检查真实构建，尤其是全文搜索。开发服务器不提供新生成的 Pagefind 索引，不应据此判断搜索故障。

## 图片与附件

文章封面和正文图片放在 src/assets/images，使用相对路径引用。例如位于 src/content/posts/example.md 的文章，可以写：

```markdown
![清楚说明图像内容的替代文本](../../assets/images/example.svg)
```

图片应先压缩，不把相机原图或视频塞入 Git。图片所在目录均视为可公开，不存放未获授权素材或保密附件。public 会原样进入站点产物，不得放入 .env、密钥、Markdown 源文档或其他私密文件。私有仓库和 draft 不是附件访问控制。

不支持直接热链远程图片，不支持在 Markdown 中插入原始 HTML；请使用标准 Markdown、代码块、公式或 Mermaid。SVG 必须是可信的自有图形，不导入来历不明的可执行内容。

## 技术内容

代码使用带语言名的围栏；公式采用 KaTeX 支持的语法，行内使用 $...$，独立公式使用 $$...$$。不支持完整 LaTeX/TikZ 工程。

流程图、时序图和分组架构图使用 mermaid 围栏。图表资源从本站加载，接近视口才渲染；异常时仍能查看源代码。复杂图可使用本地 SVG/PNG/WebP。建议添加 Mermaid 的 accTitle 与 accDescr，帮助辅助技术理解图表。

## 公开前的人工确认

- 内容、图片和引用均可公开，示例不冒充真实经历。
- 标题、摘要、时间、分类和唯一 slug 正确。
- 公式、代码、图表和图片已在手机宽度检查。
- Git 中没有密钥、私人附件和不应公开的资料。
- 设置 draft: false 后，等待所有检查通过和部署成功，再检查正式地址、搜索和 RSS。

## 修改与下架

更新正文时保留 slug，需要时填写带时区的 modDatetime。修改旧文不会把它变成一篇新发布文章。

普通下架可以改回 draft: true 后重新发布。历史部署、RSS 客户端、搜索缓存和读者副本可能仍保留旧内容；敏感撤回需要额外检查历史部署与公开附件，不能承诺清除所有外部副本。回滚前排除含有已撤回内容的旧版本。

## 项目、个人信息与示例替换

从 templates/project.md 复制到 src/content/projects/，修改唯一 slug、标题、简介、techStack。repoUrl/demoUrl/cover 都是可选字段；只填写真实、可公开的链接。私有 GitHub 仓库的链接对未授权读者可能不可用，不要把它当作公开演示地址。

关于页来自 src/content/pages/about.md；联系入口来自 astro-paper.config.ts 的 socials。没有邮箱时不预填假的地址，按需要添加真实 mailto 链接。

初始三篇文章是明确标注的演示内容，可删除或改为草稿。固定功能验收样文保存在 tests/fixtures，并只复制到隔离测试目录；最终站点校验不要求保留它们。不要直接编辑测试 fixtures 来发表文章。空文章/空项目具有明确空状态。

## 从模板到上线的完整顺序

1. 复制模板并修改元数据，先保持 draft: true。
2. pnpm dev 预览；草稿和未来文章在本地可见，确认正文与附件可以公开。
3. 用真实时间填写 pubDatetime；不要沿用模板的旧日期。改为 draft: false。
4. pnpm validate:content、pnpm test、pnpm build、pnpm verify:artifact、pnpm test:e2e；用 pnpm preview 再看生产索引。
5. git diff 复核，提交并正常推送 `codex/github-pages`，等待 **Verify and deploy GitHub Pages** 的验证与部署。
6. 正式地址、RSS、搜索和移动端均检查后，才认为这篇文章发布完成。

新增未知字段、缺失 draft、重复 slug、非法日期/图片路径等错误会带源文件路径返回。不要通过删测试或关闭校验来绕过。

公开后修改标题或移动文件不会改变 URL。移动文件时仍需调整图片相对路径。原则上不改 slug；确需迁移，需要单独设计兼容页面并验证旧链接。GitHub Pages 不应用 Cloudflare 的 `_headers` / `_redirects`，不能把这类文件当作已生效的重定向。
